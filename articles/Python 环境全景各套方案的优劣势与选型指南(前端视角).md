## 0. 先理解:为什么 Python 工具这么多

前端几乎感觉不到"环境"的存在,因为每个项目自带独立的 `node_modules`,隔离是**自动**的。

Python 不一样:默认情况下 `pip install` 的包全装进那一个"全局 Python",项目之间会互相污染。于是社区先后造出一堆工具来解决三个问题:

1. **管语言版本**(装哪个 Python、多版本切换)—— 对应前端的 nvm
2. **环境隔离**(给每个项目一份专属依赖)—— 前端天生自带,Python 要手动
3. **装依赖 + 锁版本**(可复现的依赖安装)—— 对应前端的 pnpm + lock 文件

不同工具覆盖的问题范围不同,这正是它们各有优劣的根源。看懂这三件事,下面的对比就全通了。

---

## 1. 三个核心问题 vs 各工具覆盖范围

| 工具 | 管版本 | 环境隔离 | 装依赖 | 锁版本 | 一句话定位 |
|------|:---:|:---:|:---:|:---:|------|
| **pip** | ❌ | ❌ | ✅ | 弱 | Python 自带的装包器,最基础 |
| **venv** | ❌ | ✅ | ❌(靠 pip) | ❌ | Python 自带的隔离工具 |
| **virtualenv** | ❌ | ✅ | ❌(靠 pip) | ❌ | venv 的前身,功能更全一点 |
| **pyenv** | ✅ | ❌ | ❌ | ❌ | 只管版本,像纯粹的 nvm |
| **poetry** | ❌ | ✅ | ✅ | ✅ | 依赖 + 打包一体化 |
| **conda** | ✅ | ✅ | ✅ | ✅ | 自成生态,擅长科学计算 |
| **uv** | ✅ | ✅ | ✅ | ✅ | 全能且极快,新一代方案 |

**一眼看懂:** 越往下,一个工具覆盖的问题越全。pip/venv 要好几个搭着用;uv 和 conda 一个顶一套。

## 2. 逐个拆解:优劣势与应用场景

### 2.1 pip —— Python 自带的装包器

- **是什么:** Python 官方内置的包安装工具,`pip install requests` 就是它。约等于最原始的 `npm install`,但**不管隔离、不管版本、锁版本能力弱**。
- **优势:** 人人都有,无需额外安装;生态最通用,任何教程都能直接跑。
- **劣势:** 单独用会把包全装进全局 Python,项目间互相污染;没有可靠的锁文件机制(`requirements.txt` 是手动维护,不等于 `pnpm-lock`)。
- **场景:** 几乎总是和 venv 搭配使用;或临时装个小工具。**很少单独作为项目方案。**

### 2.2 venv / virtualenv —— 隔离工具

- **是什么:** 给项目建一个独立的 `.venv` 文件夹(≈ 一份专属 `node_modules`),隔离依赖。`venv` 是 Python 3 自带的;`virtualenv` 是更老的第三方版,功能稍多、能兼容老 Python。
- **优势:** venv 零安装(标准库自带);概念简单,是理解 Python 隔离机制的基础。
- **劣势:** 只解决隔离,**不管版本、不管锁**;要手动 `activate` / `deactivate` 激活退出,容易忘;配合 pip 才能装包,是"半套"方案。
- **场景:** 想理解底层原理;极简脚本;或被现有老项目要求使用。新项目一般会被 uv/poetry 取代。

### 2.3 pyenv —— 只管版本(最像 nvm)

- **是什么:** 专门管理"装哪个 Python 版本、多版本间切换",几乎就是 Python 版的 `nvm`。
- **优势:** 版本切换干净利落;和其他工具正交,能和 venv/poetry 组合。
- **劣势:** **只管版本,不管依赖也不管隔离**,得再搭一个装包工具;Windows 支持较弱(要用 `pyenv-win` 分支)。
- **场景:** 需要在很多 Python 版本间频繁切换,且愿意自己搭配依赖工具的人。**注意:uv 已内置版本管理,装了 uv 基本不再需要 pyenv。**

### 2.4 poetry —— 依赖 + 打包一体化

- **是什么:** 用 `pyproject.toml` 管理依赖、自动建虚拟环境、生成 `poetry.lock`,还能打包发布到 PyPI。思路和 uv 很像,但出现更早。
- **优势:** 依赖解析规范、锁文件可靠;打包发布体验好;`pyproject.toml` 标准化。
- **劣势:** 速度比 uv 慢不少;**不自带 Python 版本管理**(要配合 pyenv);早期依赖解析偶有卡顿。
- **场景:** 已经在用 poetry 的存量项目;需要把库发布到 PyPI 的场景。新项目从零开始的话,uv 通常是更快的替代。

### 2.5 conda / miniconda —— 自成一套的科学计算生态

- **是什么:** 不只是 Python 包管理器,而是一整套跨语言的环境与包管理系统。能装非 Python 的二进制依赖(C/Fortran/CUDA 库等)。`Anaconda` 是全家桶(几百个预装包,约 3GB),`Miniconda` 是精简版(约 100MB,要什么自己装)。
- **优势:** 处理科学计算的**编译型二进制依赖**极省心(numpy/pandas/科学库/深度学习框架不用自己编译);能管非 Python 依赖;跨平台一致。
- **劣势:** 体积大、较重;自成生态,和 pip 混用需要注意顺序;默认会自动激活 `base` 环境、抢占 PATH,需手动关掉;日常纯 Python 开发显得"杀鸡用牛刀"。
- **场景:** **数据科学、机器学习、重度 Jupyter**,尤其是被编译型科学库折磨过的人。新手做数据方向可直接上 Miniconda。

### 2.6 uv —— 新一代全能选手(本系列主推)

- **是什么:** Rust 写的新工具,**一个工具同时干了 pyenv(管版本)+ poetry(装依赖+锁)+ venv(隔离)三件事**。心智模型高度贴近 `pnpm`。
- **优势:** 速度极快(比 pip/poetry 快一个数量级);一个工具全覆盖,命令和 pnpm 几乎一一对应;自动建 `.venv`、自动用环境,不用手动激活;连 Python 本身都能帮你下载安装。
- **劣势:** 相对年轻(但已非常成熟稳定、社区采用快);不像 conda 那样自带庞大的科学计算二进制生态。
- **场景:** **通用开发、后端、写脚本、学基础语法**——绝大多数场景的首选,尤其适合前端转过来的人。

## 3. Node → Python 概念总对照

| 作用 | 前端工具 | Python 对应 |
|------|---------|-------------|
| 管理语言版本 | nvm | pyenv / conda / **uv** |
| 切换镜像源 | nrm | 改 pip/uv/conda 的 index(配一下就行) |
| 安装依赖 | npm / yarn / pnpm | pip / poetry / conda / **uv** |
| 项目隔离 | 自动 `node_modules` | venv / conda env / **uv 自动 `.venv`** |
| 锁文件 | `pnpm-lock.yaml` | `poetry.lock` / **`uv.lock`** / `environment.yml` |
| 项目清单 | `package.json` | `pyproject.toml` |
| 交互式笔记本 | (无) | Jupyter Notebook(当成一个包装进环境) |

## 4. 怎么选:一张决策表

| 你的情况 | 推荐方案 |
|---------|---------|
| 前端转 Python,通用开发/后端/写脚本/学基础 | **uv**(首选) |
| 主做数据科学 / 机器学习 / 重度 Jupyter | **Miniconda / Anaconda** |
| 既写后端又偶尔搞数据科学 | **uv + conda 共存**(各管各的) |
| 维护已有的 poetry 老项目 | 继续用 **poetry** |
| 只想理解 Python 隔离的底层原理 | **venv + pip** 手动走一遍 |
| 需要在超多 Python 版本间切换,且已有依赖工具 | **pyenv**(否则 uv 已够) |

**给前端新手的最短路径:**

1. 默认直接上 **uv**,覆盖 90% 的日常开发。
2. 哪天要做数据科学,再**额外**装一套 **Miniconda**,和 uv 共存,互不干扰。
3. 其余工具(pip/venv/pyenv/poetry)了解概念即可,遇到老项目再按需使用。

---

## 5. 决策口诀

> **纯 Python 开发(后端/脚本/学习)→ uv;带大量编译型科学依赖(numpy/CUDA 等)→ conda。**
> 拿不准就先用 uv,不够用了再加 conda。一个项目只用一套,别混。
